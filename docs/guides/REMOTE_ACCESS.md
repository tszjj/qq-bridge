# 外网访问控制台（:3100）诊断与端口开放

> 结论先行：**外网打不开不是"防火墙没开"，而是桥接的控制台只绑定了本机回环地址 `127.0.0.1`。**
> 即使把它改成 `0.0.0.0`，还有第二道 Host 头白名单会返回 403，第三道才是云安全组。
> 三层都要动，缺一层都表现为"没有反应"。

---

## 一、为什么没反应：三层阻断

### 第 1 层：进程只监听回环（这是真正的原因）

```
netstat -ano | findstr :3100
  TCP    127.0.0.1:3100    0.0.0.0:0    LISTENING    10300
```

`127.0.0.1:3100` 表示只在**本机回环网卡**上监听。外部数据包到达 `10.0.0.5` 或公网 IP 时，
内核找不到监听该地址的套接字，直接回 RST —— 浏览器看到的就是"无法访问此网站 / 连接被拒绝"。

实测（本机执行）：

| 请求 | 结果 | 含义 |
|---|---|---|
| `curl http://10.0.0.5:3100/?token=…` | `HTTP 000`，curl 退出码 **7**（Connection refused） | 内网 IP 都连不上，公网更不可能 |
| `curl http://127.0.0.1:3100/?token=…` | `HTTP 200` | 服务本身正常运行 |
| `curl -H "Host: 10.0.0.5:3100" http://127.0.0.1:3100/api/status` | `403 Host 头不被允许` | 第二层拦截已复现 |

代码位置：`src/bridge.js` 里 `server.listen(port, '127.0.0.1', …)`。

### 第 2 层：Host 头白名单（DNS rebinding 硬化）

代码只接受三种 Host：`127.0.0.1:3100`、`localhost:3100`、`[::1]:3100`。
用 `http://10.0.0.5:3100` 或 `http://203.0.113.10:3100` 访问时，Host 头是 `IP:3100`，
不在白名单里 → 直接 403。这是有意的防护：防止恶意域名（TTL=0 解析到 127.0.0.1）
让浏览器把攻击者页面当成同源，从而绕过 Origin 校验。

**本次已改造**：新增两个可选配置 `consoleBind` 与 `consoleAllowedHosts`。
不配置时行为与改造前**完全一致**（只绑回环、只认回环 Host）。

### 第 3 层：云安全组 / 端口映射

本机网络结构：

| 项 | 值 |
|---|---|
| 内网 IPv4 | `10.0.0.5`（DHCP） |
| 公网出口 | `203.0.113.10` |
| Windows 防火墙 | Domain/Private/Public **三个配置档全部关闭**（当前不拦，但云主机不建议长期关闭） |

`10.x` 内网地址 + 独立公网 IP，说明是 **EIP/NAT 结构**：公网流量先到云的安全组，
再由 NAT 转到内网网卡。所以安全组里没放行 `3100` 时，包在 VPC 边界就被丢弃（表现为连接超时，
不是拒绝）。

## 二、端口清单（哪些要开、哪些绝不能开）

| 端口 | 协议 | 用途 | 默认监听 | 是否可对公网 | 说明 |
|---|---|---|---|---|---|
| **3100** | TCP/HTTP | QQBOT Web 控制台（总览 / 对话过程 / 收发流水） | `127.0.0.1` | **可以**，但必须限定来源 IP | 带 `consoleToken` 鉴权；能改配置、发消息、读聊天记录，泄露等于交出机器人 |
| 5099 | TCP/HTTP | SnowLuma WebUI（扫码登录 QQ、查看账号状态） | `127.0.0.1` | **不建议** | 登录态入口，暴露后可被他人接管账号；仅调试时临时开、用完关 |
| 3000 | TCP/HTTP | OneBot HTTP API（桥接发消息走这里） | `127.0.0.1` | **禁止** | 虽有 accessToken，但暴露即等于把"以机器人身份发消息"开放给全网 |
| 3001 | TCP/WS | OneBot WebSocket（事件上报） | `127.0.0.1` | **禁止** | 同上，且无二次校验 |
| 443 | TCP | 出站：WorkBuddy CLI / 腾讯云 API / QQ 协议 | — | 出站放行 | 模板已含 |
| 80 / 90 | TCP | 出站/反代（如需 Nginx 做 HTTPS） | — | 视需要 | 模板已含 |
| 53 | UDP/TCP | 出站 DNS | — | 出站放行 | 模板已有全 UDP 放通 |

**一句话原则：只开 3100，且来源写自己的固定公网 IP，不要用 `0.0.0.0/0`。**

## 三、开启步骤

### 步骤 1：改 `qq-bridge/config.json`

```json
{
  "consolePort": 3100,
  "consoleBind": "0.0.0.0",
  "consoleAllowedHosts": ["203.0.113.10", "127.0.0.1"],
  "consoleToken": "（保持原有 32 位以上随机串，不要换短密码）"
}
```

- `consoleBind`：监听地址。`127.0.0.1` = 只本机（默认）；`0.0.0.0` = 所有网卡。
- `consoleAllowedHosts`：允许的 Host（主机名或 IP，可带端口）。写 `"*"` 表示不限，
  **仅在你前面挂了 HTTPS 反代、且反代已做来源限制时才可考虑**。
- 改完**不需要改代码**，重启桥接生效（双击 `qq-bridge\start.bat`）。

### 步骤 2：Windows 防火墙（若开启）

当前三个配置档是关闭的，不用做。如果以后打开防火墙，需要放行入站 TCP 3100：

```powershell
New-NetFirewallRule -DisplayName "QQBOT Console 3100" -Direction Inbound `
  -Protocol TCP -LocalPort 3100 -Action Allow -RemoteAddress 203.0.113.10
```

`-RemoteAddress` 换成你自己的固定 IP；**不要省略这个参数**（省略等于对任何来源放行）。

### 步骤 3：云安全组

在云控制台的安全组入站规则里加：

| 来源 | 协议 | 端口 | 策略 | 备注 |
|---|---|---|---|---|
| `198.51.100.20/32` | TCP | 3100 | 允许 | QQBOT 控制台 |
| `0.0.0.0/0` | TCP | 3100 | 拒绝 | 兜底拒绝 |
| `0.0.0.0/0` | TCP | 3000,3001,5099 | 拒绝 | OneBot 与 SnowLuma 禁止公网 |

配套 CSV：`docs-bundle/05-安全与部署/防火墙规则-云服务器.csv`。

### 步骤 4：验证

```bash
# 本机：确认已绑到 0.0.0.0
netstat -ano | findstr :3100      # 期望 0.0.0.0:3100 LISTENING

# 外网机器：确认端口通
curl -sS -m 8 -o /dev/null -w "HTTP %{http_code}\n" "http://203.0.113.10:3100/?token=你的令牌"
# 期望 HTTP 200；403 = Host 白名单没配对；超时 = 安全组没放行；拒绝 = 仍绑在回环
```

浏览器打开 `http://203.0.113.10:3100/?token=你的令牌` 即可，令牌会自动存进 localStorage。

## 四、安全要求（务必遵守）

1. **令牌是唯一防线**。`consoleToken` 必须是 32 位以上随机串（`state/console-token` 里已有），
   不要改成 `123456` 之类。泄露后立刻在控制台重置并重启。
2. **优先用 SSH 隧道，而不是开放端口**（最省事也最安全）：
   ```bash
   ssh -N -L 3100:127.0.0.1:3100 user@203.0.113.10
   # 然后本机浏览器打开 http://127.0.0.1:3100/?token=…
   ```
   这样 `consoleBind` 保持 `127.0.0.1`、安全组一条都不用开，Host 头也天然合规。
3. **公网裸 HTTP 会明文传输令牌**。长期使用建议 Nginx/Caddy 反代加 HTTPS，并保留原始 Host：
   ```nginx
   location / {
     proxy_pass http://127.0.0.1:3100;
     proxy_set_header Host $host;          # 必须保留，否则 Host 白名单会 403
     proxy_set_header X-Real-IP $remote_addr;
   }
   ```
   反代时把域名写进 `consoleAllowedHosts`（如 `"bot.example.com"`）。
4. **绝对不要开放 3000 / 3001 / 5099**。前两个是 OneBot 通道，等于机器人身份；
   后者是 QQ 登录态入口。
5. 定期在控制台「运行总览」检查是否有陌生来源的登录记录（`state/bridge.log` 里搜 403/401）。

## 五、附：模板 CSV 的一个隐患

原模板第 3 行是：

```
0.0.0.0/0,ALL,ALL,允许,全部TCP、UDP、ICMP以及GRE
```

腾讯云安全组**按从上到下顺序匹配，命中第一条即生效**。这一行会把所有流量在第二位就放通，
导致后面第 7、8 行的"拒绝 44 / 拒绝 22"形同虚设。

建议：做端口白名单时删掉这条"全放通"，改为逐条放行实际需要的端口（80/443/3100 + 出站）。
配套 CSV 里已按这个思路给出（保留原行以便对照，新增行标注了建议顺序）。

## 六、当前已生效的配置（2026-11-01 17:35 更新）

`config.json`：

```json
{
  "consolePort": 3100,
  "consoleBind": "0.0.0.0",
  "consoleAllowedHosts": ["*"],
  "consoleToken": "（48 位随机串，未改动）"
}
```

按你的要求，**Host 头拦截已完全关闭**（`"*"` = 不校验）。本地实测：

| 请求 | 结果 |
|---|---|
| `netstat` | `0.0.0.0:3100 LISTENING` |
| `Host: 203.0.113.10:3100` | 200 |
| `Host: 198.51.100.20:3100` | 200 |
| `Host: bot.example.com:3100` | 200 |
| `http://10.0.0.5:3100/?token=…` | 200 |
| 不带 token | 401 |

> ⚠️ 副作用：Host 不校验等于放弃了 DNS rebinding 防护。攻击者若诱导你打开一个
> 解析到自己服务器的域名页面，浏览器会把它当作同源、能读到接口响应。
> 稳定后建议把 `"*"` 收敛成 `["203.0.113.10"]` 或具体域名。

## 七、用外部节点实测：问题不在应用层

用 4 个境外节点（奥地利 / 德国 / 日本 / 塞尔维亚）做 TCP 连通性探测：

| 端口 | 外部节点结果 | 结论 |
|---|---|---|
| **3100** | 全部 `Connection timed out` | 安全组未放行（静默丢包） |
| 3389（RDP） | **连接成功**（0.24s / 0.25s） | 入站通路正常，安全组已放行 |
| 80 | 一个 refused、一个 timeout | 无监听但有部分放行 |
| 443 | 全部 timeout | 未放行 |

**结论**：入站网络、操作系统防火墙、桥接监听、令牌全部正常，
唯一拦截是**云安全组没有 3100 的入站规则**。3389 能连上就是最好的反证——
如果安全组整体关闭，RDP 也不会通。

本实例信息（云元数据确认）：

| 项 | 值 |
|---|---|
| instance-id | `i-0000000000` |
| 地域 | `ap-beijing` |
| 公网 IP | `203.0.113.10`（已绑定本实例） |
| 内网 IP | `10.0.0.5` |

### 要做的就一步

腾讯云控制台 → 云服务器 → 实例 `i-0000000000` → 安全组 → 入站规则 → 添加：

| 来源 | 协议端口 | 策略 | 备注 |
|---|---|---|---|
| `198.51.100.20/32` | TCP:3100 | 允许 | QQBOT 控制台（你的固定出口 IP） |

保存后**立即生效**，无需重启实例或桥接。然后手机 4G 或另一台电脑打开
`http://203.0.113.10:3100/?token=…` 验证。

> 如果用的是轻量应用服务器，规则在「防火墙」页而不是「安全组」；
> 若账号开了「云防火墙」，那里也要放行一次。
> 若家庭宽带出口 IP 会变（198.51.100.20 变成别的），规则会随即失效，
> 届时把来源改成新 IP；长期方案是把来源写成固定域名解析不可行，
> 建议改用 SSH 隧道（见第四节第 2 条）。

## 八、登录页曾经白屏问题（2026-11-01 已修复）

### 现象

浏览器直接打开 `http://IP:3100/`（无 token 或 token 错误）时**一片空白**，
看不到任何登录框，DevTools 里那条文档请求是 `401` + `net::ERR_ABORTED`、DOM 为空。

### 根因（服务端设计问题，不是浏览器/网络）

旧实现把「令牌校验」放在了**页面请求**上，校验失败就返回 `401` +
一段自带 `prompt('请输入控制台访问令牌')` 的 HTML。
但 Chromium 内核对 **401 的文档响应会中止渲染**，那段内联脚本根本没有执行机会 ——
弹窗不是被浏览器拦了，是压根没跑到。

### 修法

| 请求类型 | 之前 | 现在 |
|---|---|---|
| `GET /`（页面） | 401 + 内联 prompt | **200** + 正常渲染的登录页（表单，带「令牌不正确」提示） |
| `/api/*`（接口） | 401 | **401 不变** |

只放开**页面**的状态码，鉴权本身没有放松：页面里没有任何数据，所有 API 仍由服务端校验令牌。

### 附带修复：刷新/收藏不再要求重输

带 `?token=` 成功进入时，服务端种一个 `console_token` cookie
（`SameSite=Strict`，30 天）。页面脚本原本会用 `history.replaceState` 把 token 从地址栏抹掉，
抹掉之后再刷新就没有 `?token=` 了 —— 以前每次刷新都要重新登录，现在由 cookie 补回。

> 没加 `HttpOnly`：页面需要把它同步进 `localStorage` 才能带头调 API；
> 而令牌本来就存在 `localStorage` 里，`HttpOnly` 在这里既挡不住 XSS，还只会让刷新后变成空壳。

### 验证结果

| 场景 | 结果 |
|---|---|
| `GET /` 无令牌 | **200**，渲染登录页（已截图确认，非白屏） |
| `GET /` 错误令牌 | **200**，显示「令牌不正确，请重新输入」 |
| `GET /?token=正确` | 200 + `Set-Cookie`，进入控制台 |
| 同浏览器再开 `/`（无 token） | **200 且直接进控制台**，数据正常（CLI 会话就绪 / 会话数 5） |
| `/api/status` 无令牌 | **401**（未放松） |
